Phase 1 — Grundstruktur & Polling

⬡PHP API
Datenbankschema
Zwei neue Tabellen
  • Tabelle notifications: id, user_id, type, title, body, data (JSON), is_read, created_at
  • Tabelle push_subscriptions: id, user_id, type, endpoint, p256dh, auth, user_agent, created_at — Feld type unterscheidet 'webpush' und 'unifiedpush' (schon vorbereiten)
  • Index auf (user_id, is_read, created_at) für schnelles Polling
Service-Klasse
NotificationService
  • create() — neue Benachrichtigung anlegen und optionalen Push-Versand triggern
  • getUnread() — ungelesene Items seit optionalem since-Timestamp
  • markRead() — Array von IDs als gelesen markieren
  • cleanExpiredSubscriptions() — abgelaufene Endpoints nach Bounce bereinigen
Controller & Routen
NotificationController
  • GET /notifications — ungelesene Liste, Auth required
  • POST /notifications/read — IDs als gelesen markieren
  • POST /notifications/push-subscription — Subscription speichern (vorbereitet, Phase 3/4)
  • DELETE /notifications/push-subscription — Subscription entfernen
  • GET /notifications/vapid-public-key — öffentlicher VAPID Key (kein Auth nötig)
◈Flutter App
Datenmodell
NotificationItem
  • Felder: id, type, title, body, data, createdAt
  • factory NotificationItem.fromJson() — Deserialisierung
  • data-Feld trägt optionale Routing-Info, z.B. {'route': '/forum/123'}
Service-Klasse
NotificationService
  • startPolling() — Timer starten, Intervall konfigurierbar (Standard 60 s im Vordergrund)
  • stopPolling() — bei Logout und AppLifecycleState.paused
  • markRead() — IDs an API senden
  • Stream<List<NotificationItem>> — reaktiver Stream für die UI
  • _lastSeen-Timestamp merken, damit nur neue Items abgerufen werden
App-Integration
Lifecycle & Login
  • startPolling() nach erfolgreichem Login aufrufen
  • stopPolling() bei Logout und App-Pause (Web: Page Visibility API)
  • Service als Singleton injizieren, analog zu bestehenden Services im Projekt

⬡PHP API
Kein neues Package
UnifiedPush-Versand via HTTP
  • UnifiedPush-Endpoints sind gewöhnliche HTTPS-URLs — Guzzle reicht

Bonus-Phase — FCM als stilles Weck-Signal Erst nach Phase 4

◎FCM Silent Push — nur zum Aufwecken, kein Inhalt
Konzept
FCM ohne Inhaltsübertragung

FCM sendet ausschließlich eine Data-Only-Message ohne notification-Block. Der Inhalt ist leer — nur ein Signal, das die App aufweckt. Die App pollt dann sofort die eigene API und zeigt die Benachrichtigung selbst an. Google sieht: „Weck App auf" — kein Titel, kein Text, kein Inhalt.

  • FCM-Token wie gewohnt registrieren und an API übermitteln
  • API sendet Data-Only-Message: {"data": {"ping": "1"}} — kein notification-Key
  • App empfängt Weck-Signal und triggert sofort einen Polling-Request
  • Datenschutz: Google transportiert keinen Benachrichtigungsinhalt — nur ein leeres Weck-Paket
Einordnung & Abwägung
Wann sinnvoll?
  • Als ergänzender Kanal für Nutzer ohne UnifiedPush-Distributor, die aber Google-Dienste akzeptieren
  • Verbessert Polling-Zuverlässigkeit im Hintergrund, ohne Inhalte preiszugeben
  • Nicht geeignet für Nutzer, die Google-Dienste vollständig meiden
  • Erfordert Firebase-Projekt und GoogleServices-Datei im App-Build — erhöht Komplexität
  • Erst umsetzen, wenn Phasen 1–4 stabil und im Alltag erprobt sind
